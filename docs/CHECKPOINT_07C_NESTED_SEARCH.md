# Checkpoint 07C.1 — Nested heavy model search on new HLS/SMAP features

**Status:** implemented and unit-tested in CI; real GPU workstation run pending.
**Goal:** challenge frozen Local04D on the *same* 16 target-matched
development splits with genuinely new X-only HLS/SMAP representations.

The original Checkpoint 07 plan called the Prithvi encoder experiment
"07C". This nested-search branch is **07C.1**; frozen Prithvi features
remain **07C.2**, followed by cross-fitted fusion/confirmation in 07D.
Existing naming under `checkpoint07c.py` is preserved rather than
renaming code midway through implementation.

## Search design

Five model families, with representations:

- `raw256` or `raw512`: X-only, fold-training-derived balanced
  selection across source families; imputation/scaling fitted on each
  respective training subset. No PCA used.
- `pca16`, `pca32`, `pca64`: PCA on the large X matrix,
  imputer/scaler and eigensystem fitted within the training split.

Each outer pseudo-test has **41** visible-but-unlabeled parcels and
**97** training yields. An inner 3-fold CV on the 97 labels selects
hyperparameters/representation. Only then the selected model is fit
on the 97 training labels and evaluated on the 41 held-out labels.
The 16 outer pseudo-tests overlap: they are not 16 independent
experiments. The 59 real missing yields are never read/scored.

The baseline **Local04D is frozen** from the historic OOF predictions
already scored on those same held-out parcels. Per-family model output
also includes conservative fixed 10%, 25%, 50% blends with Local04D,
which use no held-out target label for selection. These blends are
NOT a fitted residual correction: true supervised residual training
will require constructing strict cross-fitted Local04D predictions
within each outer training subset; do not improvise with stored OOF
residuals from other splits because those may have seen the current
pseudo-test yields.

## Safe execution / resumption

Use the local high-dimensional feature file generated by **full**
Checkpoint 07B. Do not use the separate 60-product 07B smoke file.

On Windows PowerShell:

```powershell
git pull --ff-only
conda activate geocebada
python -m pip install -e ".[dev,models,checkpoint07]"

# Require a visible NVIDIA GPU before long CatBoost/XGBoost work.
python tools\run_checkpoint_07c.py --preflight --device gpu

# Lightweight CPU smoke: first outer split, first two families,
# at most two Optuna trials per family. Stored in an isolated /smoke dir.
python tools\run_checkpoint_07c.py --smoke --device cpu

# Optional REAL GPU probe of CatBoost only in a separate subfolder:
python tools\run_checkpoint_07c.py --device gpu --families catboost --trials 2 --max-splits 1 --output reports/checkpoint_07c/gpu_probe

# Full resumable search across the 16 splits and all five families:
python tools\run_checkpoint_07c.py --device gpu --trials 48

# Progress at any point, from completed per-family split files:
python tools\run_checkpoint_07c.py --stage summarize
```

Do not use `--device cpu` on a full long run unless you explicitly
authorize CPU at the prompt by typing `y`. For a deliberate
noninteractive CPU batch, the separate `--yes-cpu` switch exists.

**Full-grid budget:** five families × 16 outer splits × 48 Optuna
trials × three inner folds = up to 11,520 **inner training fits**,
plus 80 outer refits. Some candidates contain up to 2,000 boosting
iterations. This is substantial compute; absolute runtime depends on
hardware/model family and is not predicted by the repo.

Every family/split has:

- a persistent `target_matched_NN__family.sqlite` with intermediate trials;
- final `target_matched_NN__family.csv` held-out predictions (41 × 5 rows);
- final `target_matched_NN__family.json` with selected parameters and
  paired Local04D/model RMSE.

A `run_spec.json` **locks** exact hashes of source data, model/PCA
code, dependency versions, CV seeds/folds, available families, device,
thread count and trial budget. Existing compatible studies resume
after an interrupted process; incompatible experiments are rejected.
If changing trial count, data version, package version or algorithm,
use a **new --output directory** under `reports/checkpoint_07c/`.
Never delete valid studies just to alter a search budget.

The default `reports/checkpoint_07c/` is gitignored: source
matrices, weights, studies and workstation predictions are NOT staged
or pushed automatically. The small published 07A/X-only snapshots
remain separate.

## Output interpretation and advancement

```powershell
Get-Content reports/checkpoint_07c/run_report.json
Import-Csv reports/checkpoint_07c/development_summary.csv |
  Sort-Object -Property rmse_mean_split |
  Select-Object -First 20 | Format-Table -AutoSize
```

The summary reports pooled, mean-split and worst-split RMSE, split
coverage and number of unique held-out parcels. Compare **only
models with all 16 splits complete**; partial models with one or two
completed splits can appear artificially good. Keep Local04D's
paired baseline in the same table.

Before promoting a model:
1. Audit feature/label splits, source missingness, failed Optuna trials,
   and any GPU execution errors.
2. Inspect stability across municipality/state, center and tails, and
   error correlations with Local04D.
3. Freeze a *small* shortlisted rule using development evidence.
4. Evaluate once on a newly designed untouched target-matched
   confirmation bank, with nested tuning still restricted to its
   training labels.
5. If a real gain is established, plan **07C.2**: pre-trained Prithvi
   embeddings for 197 × 4-frame HLS chips; then 07D fusion.
6. Keep Local04D as the canonical 59-parcel prediction source until
   evidence supports a replacement.

Do not report a fixed 10%-blend as a learned residual network.
Do not promote from these 16 reused development splits alone.
